## 1. 목적

설계 도면으로 만든 3D 모델을 실제 위성지도 위에 정합하고, 공정표의 계획 일정에 따라 구조물이 지어지는 순서를 날짜별로 재생한다. 이후 단계에서 실적 입력, 계획 대비 실적 비교, P6 / MS Project 내보내기까지 같은 데이터 구조 위에서 확장한다.

## 2. 시스템 구성 (2번 방식: 웹 기반 4D 디지털 트윈)

 교각·경간·성토구역          (일정 배분·선후행)            │
        │                       │                        │
        │                       ▼                        │
        │            ┌─ 공정 엔진 (브라우저 JS) ─┐       │

        │            │ 구조물 목록(static) →      │       │

        │            └────────────┬───────────────┘       │
        │                         ▼                        │
        │              구조물 일자표 (데이터 텍스처)        │
        ▼                         │                        │

## 4. 공정 연동 기준

### 4.1 구조물 ↔ activity 매핑

| 구조물 | 공정표 activity | 배분 방식 |
| --- | --- | --- |
| BR2-1 기초 (A1 ~ P74) | Bored pile 6팀 / 3팀 / 9팀 | 3단계를 팀 수 × 기간 비율로 분할, A1 → P74 순서 |
| BR2-1 교각·거더·슬래브 | Pier + Abut / Girder erection by gantry / Deck slab | 작업 방향 순서로 균등 배분 |
| BR2-2 (P91 → P75) + Alabang Ramp 1~4 | Main bridge 2-2 activity | 램프 교각·경간은 같은 위치 본선과 동일 일자 |
| Sucat 연결로·Ramp 2·Ramp C 교량 | Sucat Slip, Ramp Bridge activity | A-1 → P-8 → Ramp C → Ramp 2 → 루프(P-9 ~ A-2) |
| 성토부 4개 구역 | Embankment Part 구역별 세부 activity | 가물막이 → 배수 → 굴착 → 부직포·쇄석 → DSM/PVD → 성토 → Preload → 사석 → 가물막이 철거 → 포장 기층 |
| 가설잔교 | Temp. trestle (Alabang / Main) / Temp. trestle dismantling | 설치·철거 방향 순서. Alabang IC 성토 구간은 가물막이 착수 시 철거 |

### 4.2 선후행 규칙

- 기초 완료 → 교각 완료: 최소 14일
- 교각 완료 → 거더 가설: 최소 7일
- 거더 가설 → 슬래브: 최소 21일
- 모든 구조물이 해당 activity 종료일 안에 완료되는지 검증함 (위반 0건)

### 4.4 1단계 구조 전환 — 날짜를 모델에서 분리

이전 버전은 삼각형마다 날짜를 미리 계산해 GLB에 넣었기 때문에, 공정표가 바뀌면 Python 파이프라인으로 모델을 다시 만들어야 했다. Rev.1부터는 날짜를 모델에서 분리한다.

| 구분 | 이전 (Rev.0) | 현재 (Rev.1) |
| --- | --- | --- |
| GLB 정점 속성 | `_AT` = 시작일·완료일·철거일·기준고 (고정값) | `_RA` = 구조물 번호·규칙 코드·순서·기준고 (날짜 없음) |
| 날짜 계산 위치 | Python (`schedule.py` 등), 빌드 시 1회 | 브라우저 공정 엔진, 공정표가 바뀔 때마다 |
| 공정표 변경 반영 | 모델 재생성 → HTML 재조립 | `applySchedule(tasks)` 호출 1회 (약 13 ms) |
| 화면 데이터 (KPI·간트·종단면도·성토부) | HTML에 고정 내장 | 엔진 결과에서 매번 생성 |
| 착공·준공 표시 | 2027.02.26 고정 | 공정표의 `Start the work` 마일스톤, 공정표 시작·종료일에서 계산 |

**구성 파일**

| 파일 | 내용 |
| --- | --- |
| `mapping` (매핑 기준) | 교량별 시공 순서, 기초 activity와 팀 가중치, 교각·거더·슬래브 activity, 선후행 일수, 성토구역 단계별 activity, 가설잔교 설치·철거 activity, 착공 마일스톤 |
| `static` (구조물 목록) | 교각 134, 경간 132, 성토구역 4, 가설잔교 92조각 = 361개 구조물. 교각별 말뚝 본수·직경·길이, 가설잔교 조각별 진행 비율 |
| `engine` (공정 엔진) | `schedule.py`·`build_earth.py`·`build3d.py`의 일정 배분 로직을 JavaScript로 이식 |

### 4.7 공정표 불러오기 (2단계)

| 항목 | 기준 |
| --- | --- |
| 지원 형식 | MS Project XML (`.xml`), Primavera P6 (`.xer`). 한글 인코딩(UTF-8·EUC-KR) 자동 판별 |
| `.mpp` 원본 | 브라우저에서 해석 불가(비공개 형식). MS Project에서 [파일 → 다른 이름으로 저장 → XML 형식]으로 저장해서 업로드. `.mpp`를 올리면 이 안내를 표시 |

### 4.11 착공일 이동 (Rev.4, 0단계)

착공일을 바꾸면 공정표 전체가 같은 작업일 수만큼 이동한다. 선행작업이 없는 activity와 요약 activity도 함께 옮긴다. 이동 폭은 공정표 파일의 캘린더로 센다(re3: Standard, 월~토 근무).

| 항목 | 기준 |
| --- | --- |
| 입력 위치 | 공기 현황 카드 → 연필(편집) → 착공일 |
| 계산 | 이동 작업일 = 새 착공일의 작업일 번호 − 원본 착공 마일스톤(Commencement)의 작업일 번호. 각 activity의 시작·완료를 같은 작업일 수만큼 옮김. 휴일에 걸친 날짜는 휴일 간격을 유지 |
| 휴일 입력 | 새 착공일이 휴일(일요일)이면 다음 작업일로 조정하고 카드에 표시 |
| 계약 | 계약 착공일 = 공정표 착공일, 계약 준공일 = 착공일 + 36개월(같은 날짜) |
| 저장 | 브라우저 설정 키 `llrn4d-contract-v2` (Rev.3의 `llrn4d-contract`는 계약 날짜만 바꾸던 값이라 쓰지 않음). 공정표 원본은 그대로 두고 화면을 열 때마다 이동 계산 |
| 검증 (2027.03.01) | +234작업일, activity 2,047개 모두 이동(선행 없는 5개 포함), 작업일 기준 기간 불일치 0, 관계 계산 재현 2,045/2,047 유지, 주공정·여유 변화 0, 계획 준공 2030.03.01 = 계약 준공 2030.03.01 |

달력 날짜로는 36개월 안의 일요일 수가 착공일마다 하루쯤 다를 수 있다. 그러면 계획 준공과 계약 준공이 ±1일 어긋날 수 있으며, 이는 계산 오류가 아니라 캘린더 차이다.

### 4.14 실적·실적기반 공정표 (Rev.5, 1단계)

실적은 세부 activity에만, activity 고유 ID(uid) 기준으로 입력한다. 요약 행은 자식에서 자동 집계한다. 날짜는 현장 시각(UTC+8) 기준이다.

| 항목 | 기준 |
| --- | --- |
| 입력값 | 실제 착수일, 진척률(%), 실제 완료일. 완료일을 넣으면 100%, 100%를 넣으면 완료일 = 기준일(고칠 수 있음). 기준일 이후 날짜는 받지 않음 |
| 기준일 | 실적을 마감한 날. 남은 작업은 그 다음 작업일부터 계산 |
| 계산 방식 | P6 기본값과 같게: Retained logic(진행 중 activity의 남은 작업은 미완료 FS 선행이 끝난 뒤), 남은 기간 = 원기간 × (1 − %) 를 시간(8h) 단위로 반올림, 공정표 파일의 캘린더(re3 Standard 월~토) |
| 결과 | activity별 실적·예상 시작/완료, 계획 대비 완료 차이(작업일), 실적기반 여유·주공정, 예상 준공일 |
| 검증 | 실적 없음 → 예상 일정이 관계 계산(CPM)과 2,047개 모두 일치. 기준일까지 계획대로 입력 → 예상 완료 2,047개 모두 계획과 일치(준공 2030.03.01). 진행 중 주공정 activity의 남은 작업 +15작업일 → 예상 준공 +15작업일 |
| 공정률 | 작업기간 가중(계획 기간 길이를 가중치로). 계획 곡선 = 계획 일정, 실적 곡선 = 기준일까지 실적, 이후 = 실적기반 예상 |

**보기 모드 (4D 조감도)**

| 모드 | 3D 표현 |
| --- | --- |
| 계획 | 계획 공정표 그대로 (기존) |
| 실적·예상 | 기준일까지 실적, 이후 실적기반 예상으로 재생. 흰색 반투명 = 예상 일정상 앞으로 지어질 구조물 |
| 계획 대비 | 실적·예상으로 지어진 모습에 색 표시: 빨강 = 계획보다 7일 넘게 늦음, 파랑 = 7일 넘게 앞섬. 연빨강 반투명 = 계획상 그 날짜에 있어야 하는데 아직 없는 구조물 |

공정표(간트)에는 실적·예상 막대를 계획 막대 아래에 얇게 그린다(빨강 = 계획보다 7일 넘게 늦은 완료). S-curve는 계획·실적·예상 3선과 기준일·계약 준공일을 표시한다.

**데이터 파일**

| 항목 | 기준 |
| --- | --- |
| 파일 | `LLRN_CP1B_실적.json` (연결한 폴더, 기본 `00 조감도_GIS/data`) |
| 내용 | 기준일, 실적, 변경분 기록(누가·언제·무엇을), 기준일별 요약(snapshot), 착공일·계약 공기, 업로드한 공정표(기본 re3는 앱에 내장이라 넣지 않음) |
| 저장 | [저장] 때 기존 파일을 `history/LLRN_CP1B_실적_YYYYMMDD-HHMM.json`으로 보관한 뒤 덮어씀 |
| 동시 수정 | 마지막으로 읽은 뒤 파일 수정시각이 바뀌었으면 저장 전에 알림 (불러오기 / 덮어쓰기 선택) |

### 4.15 공정표 기준선 (Revision) (Rev.5a)

공정표를 수정해도 이전 계획은 지우지 않고 기준선으로 쌓는다. Rev.0 = 계약 공정표(최초 계획), Rev.1 이후 = 수정 공정표.

| 항목 | 기준 |
| --- | --- |
| 현재 기준선 | 실적기반 공정표 계산(논리·기간), 공정표(간트), 주공정, 공기 현황 카드에 쓰는 계획 |
| 비교 기준선 | 지연 일수(실적 입력 표, 구조물 클릭), S-curve 계획선, 4D "계획 대비" 색, 실적 현황 카드의 기준. 기본 = Rev.0 (공기연장 근거), 현재 기준선으로 바꾸면 현장 관리용 |
| 실적으로 새 기준선 만들기 | 기준일까지 끝난 activity = 실제 착수·완료일(기간도 실제 작업일), 진행 중 = 실제 착수일 + 남은 기간(원기간 × (1 − %)), 이후 = 실적기반 공정표 일정. 실적을 기준선 안에 고정해 두어 주공정 계산도 그 기준일 기준으로 함 |
| 수정 공정표 올리기 | P6·MS Project로 다시 짠 파일을 [새 기준선(Rev.n)으로 추가]. 같은 ID의 activity는 실적 날짜로 맞추고, 기준일 이후는 파일의 관계대로 다시 계산(파일 날짜와 달라진 activity 수를 알려 줌) |
| 실적 이관 | 새 파일에 같은 ID가 없는 실적은 이름·상위 공종 유사도로 후보를 제시(60% 이상이면 자동 선택). 고르지 않은 실적은 그 기준선에서 빠지고 데이터 파일에는 남음 |
| 착공일 | Rev.0에서만 옮길 수 있음. Rev.1 이후는 실제 날짜라 고정 |
| 파일 교체 | "현재 기준선 바꾸기"와 "기본 공정표(re3)로 되돌리기"는 Rev.0이 현재일 때만 |
| 상태 | 작성 중 / 제출 / 승인 (승인 일시 기록). 이름은 표에서 바로 고침 |
| 저장 | 데이터 파일 `baselines`에 모두 저장 (Rev.0이 내장 re3이면 공정표 본문은 넣지 않음). `active`·`cmp`에 현재·비교 기준선, 기준일별 요약에도 어느 기준선과 비교했는지 기록 |

**검증 (예시 실적, 기준일 2027.12.31)**: 실적으로 만든 Rev.1을 다시 계산하면 2,047개 모두 같은 날짜(주공정 계산 2,047/2,047 재현), Rev.1 대비 지연 0개·예상 준공 차이 0일, 기준일 계획 공정률 = 실적 공정률(16.19%). Rev.0 대비로는 예상 준공 +31일, 지연 activity 833개 그대로. 수정 공정표(ID 5개 변경) 업로드 시 5건 모두 같은 activity로 자동 연결.

S-curve 색: 비교 기준선 = 회색, 현재 기준선(다를 때) = 황색(#c27a00), 실적·예상 = 파랑. 색각 이상 구분 검사 통과(보라는 파랑과 구분이 안 돼 쓰지 않음).

### 4.16 가상 현장 · 메신저 시뮬레이터 (Rev.6, 2단계)

실제 착공 전에 "계획 발송 → 회신 → 해석 → 검토 → 실적 반영 → 실적기반 공정표" 전체 흐름을 가상 작업반으로 돌려 보는 기능이다. 메시지 형식은 4단계 Telegram 봇과 같다.

| 항목 | 기준 |
| --- | --- |
| 작업반 | 김민수 반장(Bored pile, 번호형 회신), R. Santos 반장(하부공, 한국어 문장), 이정훈 과장(성토·지반개량, 짧은 혼합 문장), J. Reyes 협력사(가설잔교·거더 제작, 영어), M. Cruz 반장(상부공·부대공, "1번 30" 형) |
| 작업 배정 | WBS 경로로 자동: Temporary Bridge·Fabrication·Removal → Reyes, Schedule of Bored Pile → 김민수, Super structure·Other work → Cruz, Substructure → Santos, Slip Road 성토·지반개량 → 이정훈, 그 외(마일스톤·서류) → 공무 직접 기록 |
| 하루 흐름 | 07:00 작업반별 계획(번호 목록, 어제까지 진척) → 17:00~20:00 회신(일부는 22:40 또는 다음 날 06:30 늦은 회신) → 해석 → 검토함 → 21:00 마감, 기준일을 그날로 이동. 휴일(공정표 캘린더 일요일)은 건너뜀 |
| 하루 계획 고르기 | 그날 진행 중인 작업 + 실적기반 공정표에서 시작일이 된 작업. 주공정 작업을 먼저, 작업반별 동시 작업 수 한도(6~12개) |
| 시나리오 | 정상 / 우천(30% 확률로 비: 성토·가설 작업 중지, 나머지 생산성 50%) / 장비 고장(하부공 3~7일째 중지) / 생산성 저하(Bored pile 70%) / 복합 |
| 회신 해석 | 번호형("1. 60%", "2번 끝")은 그날 계획 번호로 연결. 자유 문장은 위치(P61, A1, R2-3, Span 30, Sucat/Alabang) + 공종 단어(파일캡, 코핑, 시트파일, 성토, PVD…)로 그날 계획 항목 중에서 찾고, 없으면 그 작업반의 미완료 작업 전체에서 찾음(신뢰도 75% 이하로 낮춰 검토함에 남김). 위치는 맞는데 공종이 다르면 다른 작업으로 봄 |
| 진척과 중지 | "50%, 비 때문에 중지"처럼 둘 다 있으면 진척률을 기록. 중지만 있으면 중지 사유(우천·장비 고장·자재·기타)를 기록 |
| 날짜 | 현장 시각(UTC+8) 07:00 전에 온 회신은 전날 실적 |
| 검토함 | 회신 문장, 해석한 activity(바꿀 수 있음), 진척/완료/중지, 신뢰도. [반영]·[무시]. "신뢰도 80% 이상 자동 반영"을 켜면 번호형과 위치·공종이 분명한 문장은 바로 반영 |
| 확인 답장 | 반영 후 작업반에 "반영했습니다 ✓ · P61 · Pilecap — 완료" 형식으로 답장 |
| 해석 정확도 (가상 정답 비교, 31일) | 번호형 100%(약 200건), 자유 문장 97.2~99.2%(약 500건). 계획의 합격 기준(번호형 100%, 자유 문장 90%)을 넘음 |
| 속도 | 1개월 진행 node 0.8초, 브라우저 약 4초 |
| 저장 | 가상 현장 상태(정답 진척, 계획, 메시지, 검토함)도 데이터 파일에 저장하되 파일 이름은 `LLRN_CP1B_가상현장.json` (실제 `LLRN_CP1B_실적.json`과 섞이지 않음) |
| 수신함 파일 | `data/inbox/*.jsonl` 한 줄 = 메시지 하나 (`id`, `at`, `from`, `text`). [수신함 파일 읽기]가 같은 검토함으로 넣음. 4단계 봇은 이 파일에만 씀 |

자유 문장 해석은 지금은 규칙 기반이다. 4단계에서 Claude API를 붙이면 규칙으로 못 찾은 문장(신뢰도 낮음)을 API에 물어 후보를 고른다.

## 7. 운영 환경

| 항목 | 요구 사항 |
| --- | --- |
| 브라우저 | Microsoft Edge / Chrome 최신 버전, WebGL2(그래픽 가속) 활성 |
| 인터넷 접속 | `cdn.jsdelivr.net` (CesiumJS·Pretendard), `server.arcgisonline.com` (위성지도) |
| 로컬 파일 실행 | 브라우저는 로컬 파일(`file://`)에서 CesiumJS의 백그라운드 작업(Web Worker)을 차단하므로, Cesium 기본 지구본 대신 위성 타일을 지표면 도형으로 직접 그려 서버 없이 더블클릭으로 실행되게 함 |
| 오프라인 | 3D 모델·공정 데이터는 파일에 내장. CesiumJS를 내려받을 수 없으면 3D만 안 보이고 공정 현황·종단면도·공정표는 동작 |
| 파일 크기 | 약 9.5 MB (GLB 5.2 MB, re3 공정표 2,345행·엔진·불러오기·매핑 포함) |
| 브라우저 저장소 | 업로드 공정표·계약 공기 수정값·화면 테마를 PC별 브라우저에 저장. 다른 PC나 다른 브라우저와는 공유되지 않음 |

## 8. 데이터 갱신 절차

**공정표만 바뀐 경우** (Rev.2부터 화면에서 처리)

1. MS Project에서 XML로 저장하거나 P6에서 XER로 내보낸다.
2. 앱의 [공정표 불러오기]에서 파일을 올리고, "확인 필요"·"미연결" 항목만 점검한 뒤 [적용]을 누른다.
3. 3D·KPI·종단면도·공정표·주공정·공기 현황이 새 공정표 기준으로 바로 바뀐다.

**형상이 바뀐 경우** (도면 개정)

1. 3D 형상을 갱신하고 `build_rules.py`로 삼각형별 구조물 번호·규칙 코드를 다시 부여한다.
2. `build_glb2.py`로 GLB를, `assemble.py`로 HTML을 다시 만든다.
